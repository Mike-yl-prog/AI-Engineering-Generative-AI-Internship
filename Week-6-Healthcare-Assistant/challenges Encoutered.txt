Challenges Encountered

During Week 5, several challenges were encountered while moving from the assistant design stage to practical implementation. The main technical challenge was integrating the Flask application with the locally hosted Ollama LLM and ensuring that user messages could successfully travel from the frontend to the model and back to the chat interface. Additional effort was required to refine the user interface and create a larger, clearer conversation area.

Another significant challenge involved establishing appropriate healthcare safety boundaries. The assistant needed to remain useful for administrative and clinic-information requests without providing medical diagnoses, treatment recommendations, or unsupported clinical information. This required explicit prompt instructions and the development of safety and escalation test scenarios.

Knowledge grounding was also an important challenge. Since the HealthConnect assistant must operate within the approved Clinic Knowledge Base, the system needs to avoid inventing clinic policies or information when the required information is unavailable. This led to the decision to prioritise Knowledge Base grounding and fallback responses.

Finally, testing the assistant required more than checking whether it could answer simple questions. Supported, ambiguous, unsupported, medical, urgent, and unavailable-information scenarios needed to be considered to evaluate whether the prototype behaved consistently with its intended scope.

These challenges helped refine the implementation approach and identified areas requiring further development in Week 6.

Additional Challenges Encountered
1. Model Response Timeout

The HealthConnect Assistant initially experienced HTTP read-timeout errors when communicating with the local Ollama server.

The timeout was initially set to 70 seconds, but the model sometimes did not return a response within that period. Increasing the timeout to 180 seconds allowed more time for the local model to respond during testing.

However, testing showed that increasing the timeout alone does not solve the underlying performance issue. This led to further investigation of model response time and hardware utilisation.

2. Local Model Performance

The Ollama model was found to be using approximately 97% CPU and only 3% GPU during inference.

This highlighted a potential performance bottleneck and showed that response speed depends not only on the Flask application but also on the local model and available hardware resources.

3. Model Output Testing

Another challenge was discovering that a working model does not necessarily produce correct or approved answers.

For example, when asked about payment methods, the assistant invented payment options such as cash, Visa, Mastercard, and Amex, even though these details were not included in the approved HealthConnect Knowledge Base.

This demonstrated the importance of testing the actual model output, rather than only testing whether the application and API were functioning.

4. Unsupported Insurance Information

When asked whether insurance would cover a consultation, the model provided speculative information about possible insurance coverage.

This violated the system requirement that the assistant must not invent or guess insurance coverage.

The issue highlighted the need for specific negative and adversarial test cases to ensure that the model refuses to provide information that is unavailable in the Knowledge Base.

5. Difference Between Model Testing and Application Testing

Testing the model directly with Ollama produced different behaviour from testing it through the HealthConnect application.

When Ollama was tested directly, the model did not know about the fictional HealthConnect Clinic and generated information about a different organisation.

When the model was accessed through the Flask application, the HealthConnect system prompt was included and the assistant correctly identified itself as the HealthConnect Healthcare Information Assistant.

This demonstrated that the same model can behave differently depending on the instructions and context provided by the application.

6. Discovering Problems Through Testing

An important lesson from development was that writing the code is only one part of building the system.

Testing different user inputs revealed problems that were not immediately obvious from the implementation itself.
